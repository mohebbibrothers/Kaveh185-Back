# «بدونِ کد وارد آزمون شدم» — تشخیص و پاک‌سازیِ دادهٔ آزمایشی

> ⚠️ **وضعیتِ فعلی: کدِ تأیید خاموش است** (`BALE_OTP_MANDATORY=false`) — تصمیمِ
> صریحِ کارفرما در آزمونِ میدانی: کاربر اطلاعات را می‌زند و دکمهٔ «ورود به آزمون»
> برایش می‌آید. بقیهٔ این سند ابزارِ تشخیص است و برای **زمانی که سیاست را دوباره
> روشن کردید** کاربرد دارد (`BALE_OTP_MANDATORY=true` در `.env`، بدونِ تغییرِ کد).


> این سند برای حالتی است که کاربر می‌گوید کد نیامده ولی وارد آزمون شده.
> دو ابزار دارد و هیچ‌کدام راز چاپ نمی‌کنند.

## ۱. سه لایه‌ای که باید بسته باشند

ورود به آزمون سه دروازه دارد. اگر یکی باز باشد، کاربر بی‌کد وارد می‌شود:

| لایه | شرط | کجا |
|---|---|---|
| ثبت‌نام | `BALE_OTP_MANDATORY=True` | `apps/authentication/services.py` |
| نشست | همان شرط، در `IsVerifiedParticipant` | `apps/authentication/permissions.py` |
| فرانت | `otp_required=true` ⇒ گامِ کد | `front/src/widgets/register/RegisterForm.tsx` |

⚠️ **مهم‌ترین تله:** `git pull` فقط فایل‌ها را روی دیسک عوض می‌کند. اگر
**اپلیکیشن پایتون را در cPanel ری‌استارت نکنید**، Passenger همان کدِ قدیمیِ
داخلِ حافظه را اجرا می‌کند و باگ سرِ جایش می‌ماند. `BALE_OTP_MANDATORY=True`
چاپ‌شدن در شل هم چیزی را ثابت نمی‌کند؛ آن شل یک پروسهٔ جدا است.

## ۲. تشخیصِ قطعی — `verify_otp_gate`

```bash
cd ~/Kaveh185-Back
PY=~/virtualenv/Kaveh185-Back/3.12/bin/python
$PY manage.py verify_otp_gate
```

سه چیز را چاپ می‌کند:

1. **هشِ فایل‌های `services.py` و `permissions.py`** + اینکه آیا نشانهٔ رفعِ باگ
   داخلشان هست (اگر نه: `git pull` انجام نشده).
2. مقدارِ زندهٔ `BALE_OTP_MANDATORY` و سوئیچِ ادمین.
3. **آزمونِ واقعی**: یک کاربرِ تأییدنشدهٔ موقت می‌سازد، توکن می‌دهد و
   `POST /api/v1/exam/start/` را اجرا می‌کند؛ انتظار `HTTP 403` با کدِ
   `otp_verification_required`. کاربرِ موقت در پایان پاک می‌شود.

اگر خروجی «درگاه بسته است» بود ولی مرورگر خلافش را نشان می‌دهد، مشکل سمتِ
بک‌اند نیست: کش/نشستِ مرورگر یا نسخهٔ قدیمیِ فرانت است (بخشِ ۴).

## ۳. کالبدشکافی و پاک‌سازیِ دادهٔ آزمایشی — `reset_test_participants`

اول **بدونِ آرگومان** (فقط گزارش، هیچ حذفی):

```bash
$PY manage.py reset_test_participants
```

برای هر شرکت‌کننده می‌نویسد: شمارهٔ پوشیده، پرچمِ تأیید، داشتنِ آزمون،
تعدادِ کدهای تأییدشده، و **مسیرِ ثبت‌نام** از لاگِ ممیزی:

| مسیر | معنی |
|---|---|
| `otp ✔` | سالم — کد آمده و تأیید شده |
| `fast_direct ⚠ (باگ)` | از مسیرِ قدیمیِ معیوب وارد شده |
| `—` | لاگِ ممیزی برایش نیست (دادهٔ seed یا قبل از افزودنِ لاگ) |

نشانهٔ قطعیِ باگ: **`is_phone_verified=True` ولی صفر کدِ تأییدشده**.

سپس یکی از دو حالت:

```bash
# الف) همه‌چیز پاک شود؛ شماره‌ها آزاد می‌شوند (برای تستِ کاملِ ثبت‌نام)
$PY manage.py reset_test_participants --yes

# ب) کاربران بمانند ولی آزمون/کدها پاک و پرچمِ تأیید برداشته شود
#    (برای تستِ «همان شماره، آیا کد می‌آید؟»)
$PY manage.py reset_test_participants --yes --keep-users
```

هر دو حالت:
- فقط کاربرانِ `role=participant` را می‌زنند؛ **ادمین/اپراتور هرگز حذف نمی‌شوند**.
- آزمون‌ها، کدهای یک‌بارمصرف، نشست‌ها، سیگنال‌های ریسک، لاگ‌های پیامک و
  اشتراک‌های بلهِ مرتبط را پاک می‌کنند.
- شمارندهٔ denormalized مسجدها (`registered_count`) را از صفر بازسازی می‌کنند.

⚠️ لاگِ ممیزی (`AuditLog`) زنجیرهٔ هشِ فارنزیک است و **عمداً حذف نمی‌شود**؛
فقط رکوردهای مرتبط با کاربرانِ حذف‌شده با `user=NULL` باقی می‌مانند.

## ۴. بعد از پاک‌سازی، تستِ انسانی

1. `cPanel → Setup Python App → Restart` (اجباری؛ بدونِ این کدِ قدیمی می‌ماند).
2. مرورگر: پنجرهٔ ناشناس (کش و کوکیِ `kaveh185_access` پاک شود).
3. ثبت‌نام ⇒ باید **صفحهٔ کد** بیاید، در `@kaveh185_bot` کد برسد، و تا
   تأییدِ کد هیچ ورودی به آزمون نباشد.
4. سپس `$PY manage.py verify_otp_gate` و انتظارِ «درگاه بسته است».

## ۵. ریشهٔ باگ (برای مرجع)

`register_or_enter_participant` وقتی سوئیچِ ادمین
`require_otp_before_exam=False` بود، خودش `is_phone_verified=True` می‌گذاشت و
توکن می‌داد. چون این پرچم **روی رکورد کاربر ذخیره می‌شد**، حتی بعد از رفعِ
باگ هم آن حساب‌ها «تأییدشده» می‌مانند و مستقیم وارد آزمون می‌شوند. رفعِ کد
تنها نمی‌تواند گذشته را برگرداند؛ برای همین پاک‌سازی/برداشتنِ پرچم لازم است.
