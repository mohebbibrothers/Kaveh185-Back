# تشخیصِ «رباتِ بله پاسخ نمی‌دهد» — از ریشه، شاخه‌به‌شاخه

> وضعیتِ فعلی (آزمونِ `bale_doctor`): **هفت لایه سبز است** — توکن، کلید، نشانی،
> ثبت، دسترس‌پذیری، پاسخِ خودِ اپلیکیشن (۲۰۰ + `handled=start`)، و بی‌خطایی در بله.
> تنها چیزی که **ثابت نشده** این است: بله تا حالا یک آپدیت به این اپ **تحویل**
> داده باشد (دفترِ تحویل خالی است) و پایشِ ۱۲۰ ثانیه‌ای هیچ تغییری در صف ندید.

پس مسئله در کدِ ما نیست؛ در **رسیدنِ پیام از بله به اپ** است. چهار حالت ممکن
باقی می‌ماند و هر کدام آزمونِ جداگانه دارد.

---

## ۱) چرا «صف = ۰» به‌تنهایی هیچ چیز را ثابت نمی‌کند

`pending_update_count` شمارندهٔ آپدیت‌هایی است که بله **نتوانسته تحویل بدهد**.
اگر بله `getUpdates` یا `setWebhook` را تازه ببیند، صف را صفر می‌کند؛ و اگر
کاربر هیچ آپدیتِ **تازه‌ای** نسازد، صف صفر می‌ماند — با اینکه هیچ چیز تحویل نشده.
به همین دلیل سراغِ آزمون‌هایی رفتیم که **آپدیتِ اجباری** می‌سازند.

---

## ۲) آزمونِ A — تلنگرِ سمتِ بله (بدونِ دخالتِ شما)

```bash
PY=~/virtualenv/Kaveh185-Back/3.12/bin/python
$PY manage.py bale_doctor --fix --nudge
```

`deleteWebhook` + `setWebhook` انجام می‌شود (صف دور ریخته نمی‌شود) و تا ۶۰ ثانیه
منتظرِ رسیدنِ آپدیت می‌مانیم.

| نتیجه | معنا | کارِ بعدی |
|---|---|---|
| `✓ بله تحویل داد!` | بله سالم تحویل می‌دهد؛ مشکل قبلی موقتی/مربوط به آپدیتِ تکراری بوده | برو در بله پاسخ را ببین؛ اگر نبود `bale_check` |
| `✗ هیچ آپدیتی نفرستاد` | هیچ آپدیتِ معلقی در صفِ بله نیست | آزمونِ B |

## ۳) آزمونِ B — آزمونِ کنترلِ کران (این یکی قبلاً **قطعی** کار کرد)

مسیرِ polling در همین پروژه روی همین سرور، پنج پیامِ شما را خواند. اگر الان هم
بخواند، یعنی: توکن و شبکه و ربات سالم‌اند و **فقط تحویلِ وب‌هوک** می‌لنگد.

```bash
$PY manage.py bale_webhook --delete      # وب‌هوک را بردار (polling آزاد شود)
$PY manage.py bale_inbox --verbose       # در بله یک پیام بفرستید، بعد این را بزنید
```

| نتیجه | معنا |
|---|---|
| `update=… text='/start'` و پاسخ آمد | ربات کامل سالم است ⇒ مسئله ۱۰۰٪ تحویلِ وب‌هوک |
| `وب‌هوک فعال است (…)` | حذف انجام نشده؛ `--delete` را دوباره بزنید |
| `۰ پیام خوانده شد` | پیام به ربات نمی‌رسد ⇒ چتِ ربات در بله/فیلترِ سمتِ کاربر |

بعد از این آزمون، دوباره وب‌هوک را برگردانید:

```bash
$PY manage.py bale_doctor --fix
```

---

## ۴) آزمونِ C — پیامِ **تازه**، نه «شروع»ِ تکراری

`/start` در بله فقط **یک‌بار** دکمهٔ «شروع» می‌سازد. اگر قبلاً شروع کرده باشید،
زدنِ دوبارهٔ آن معمولاً آپدیتِ تازه نمی‌سازد. آزمونِ درست:

1. در گفتگو یک **متنِ سادهٔ تازه** بفرستید: `سلام` یا شمارهٔ خودتان.
2. بلافاصله: `$PY manage.py bale_doctor --deliveries 5`

اگر دفتر پر شد ⇒ کانال کامل است و فقط `/start` تکراری بی‌اثر بوده.

---

## ۵) آزمونِ D — حذفِ ربات از گفتگو و شروعِ دوباره

اگر آزمون‌های B و C هم چیزی نشان ندادند، ربات را در بله **حذف/بلاک** و بعد
دوباره از `@kaveh185_bot` شروع کنید. این «آپدیتِ شروع» را در سمتِ بله قطعی
می‌سازد.

## ۶) راه‌حلِ تضمینی — کران (اگر وب‌هوک به هر دلیل تحویل ندهد)

روی این هاست ثابت شده که polling کار می‌کند. کران، وب‌هوک را دور می‌زند:

```bash
$PY manage.py bale_webhook --delete
crontab -e
```

```
* * * * * cd /home/kavehir/Kaveh185-Back && /home/kavehir/virtualenv/Kaveh185-Back/3.12/bin/python manage.py bale_inbox >> /home/kavehir/kaveh185_bale.log 2>&1
*/2 * * * * cd /home/kavehir/Kaveh185-Back && /home/kavehir/virtualenv/Kaveh185-Back/3.12/bin/python manage.py deliver_outbox >> /home/kavehir/kaveh185_outbox.log 2>&1
```

تأخیرش تا ۶۰ ثانیه است، ولی **کار می‌کند** — و برای شروعِ مسابقه کافی است.
اگر بعداً خواستید به وب‌هوک برگردید، `$PY manage.py bale_doctor --fix` کافی است.

## ۶٫۵) نتیجهٔ نهاییِ آزمون (قطعی) و راه‌حلِ برگزیده

| آزمون | نتیجه |
|---|---|
| `--nudge` (تحویلِ اجباری از بله) | ✗ بله هیچ آپدیتی نفرستاد |
| کنترلِ کران (`bale_inbox --verbose`) | ✓ **۱۷ آپدیت خواند** و ۵ پاسخ با ✓ ارسال شد |
| دفترِ تحویل | ✓ `polling · start · پاسخ=✓` |

جمع‌بندی: **بله وب‌هوکِ این دامنه را تحویل نمی‌دهد** (ثبت می‌کند، `pending_update_count`
صفر گزارش می‌کند، ولی ۱۷ آپدیت در صف می‌مانند). کدِ ما سالم است.
پس مسیرِ رسمی = **long-polling به‌صورتِ سرویسِ همیشه‌بیدار**:

```bash
$PY manage.py bale_webhook --delete      # وب‌هوک را بردار (اگر هست)
$PY manage.py bale_worker --status       # باید «وب‌هوک ثبت نیست» بگوید
$PY manage.py bale_worker                # اجرای پیوسته؛ پاسخ در < ۱ ثانیه
```

برای اینکه بعد از بستنِ ترمینال زنده بماند:

```bash
# اگر systemd دارید:
sudo cp deploy/cpanel/bale_worker.service /etc/systemd/system/
sudo systemctl enable --now bale_worker && sudo journalctl -u bale_worker -f

# اگر Supervisor دارید (cPanel):
cp deploy/cpanel/bale_worker_supervisor.conf ~/supervisord.conf.d/
supervisorctl reread && supervisorctl update
```

و یک خط کران فقط به‌عنوانِ **نجات‌بخش** (اگر سرویس مُرد، حداکثر یک دقیقه بعد):

```
* * * * * cd ~/Kaveh185-Back && ($PY manage.py bale_worker --status | grep -q "زنده است" || $PY manage.py bale_worker --once >> ~/kaveh185_bale.log 2>&1)
```

مزیت‌ها نسبت به کرانِ ساده: پاسخِ آنی (نه تا ۶۰ ثانیه)، پردازشِ تضمینیِ
تک‌نمونه (قفلِ فایل)، بازگشتِ نمایی در خطای شبکه، ثبتِ قلبِ زندگی، و خروجِ
تمیز با `SIGTERM`.

## ۷) کارهایی که **همین حالا** باید انجام شود (امنیت)

| مورد | چرا | دستور |
|---|---|---|
| توکنِ ربات | در چت عمومی افشا شد | در بله `/revoke` یا از `@BotFather` توکنِ تازه → `.env` |
| `BALE_WEBHOOK_SECRET` | در چت افشا شد | `$PY manage.py bale_webhook --new-secret` → خطِ چاپ‌شده را در `.env` → `$PY manage.py bale_doctor --fix` |

## ۸) آنچه در این مسیر ساخته شد (و حالا نگهبانِ همین مشکل است)

- `bale_doctor` — هفت لایه، یک حکم؛ `--fix`، `--watch`، `--nudge`، `--deliveries`، `--report`.
- `BaleDeliveryLog` — دفترِ تحویل: هر آپدیت، مسیرش، و اینکه پاسخ **واقعاً** رفت یا نه.
- `csrf_exempt` روی ویو، خواندنِ بدنهٔ خام، ۲۰۰ به‌جای ۵۰۰، `hmac.compare_digest`.
- `BALE_WEBHOOK_URL` رسمی + ترجیحِ `api.` به `www`.
- `notifications/probe.py` — یک منبعِ حقیقتِ مشترک برای سنجه‌ها.
