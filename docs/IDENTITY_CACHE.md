# کشِ هویت و نشستِ خودترمیم — معماری

این سند توضیح می‌دهد چرا در دورِ ۴۹ یک لایهٔ تازه به نام **کشِ هویت** اضافه
شد، چه مسئله‌ای را حل می‌کند، و اگر روزی خواستید تغییرش دهید چه چیزهایی
نباید بشکنند.

## مسئله (به زبان کاربر)

> «بعد از ثبت‌نام از صفحهٔ آزمون به خانه می‌روم؛ دوباره «ثبت‌نام و شرکت» را
> می‌زنم و به‌جای شروعِ آزمون، همان فرمِ ثبت‌نام می‌آید و اطلاعاتم ذخیره
> نشده.»

این یک باگ نیست؛ **چهار** باگ با یک نمودِ بیرونی است.

## چهار ریشه، چهار درمان

| # | ریشه | نشانه | درمان در این دور |
|---|---|---|---|
| ۱ | دکمهٔ هدر همیشه به `/register` می‌رفت | کاربرِ ثبت‌نام‌شده به فرمِ خالی می‌رسید | `EntryCta` از `useIdentity()` می‌خواند؛ مقصد `next.path` است که **سرور** تعیین می‌کند |
| ۲ | `/register` نشست را نمی‌دید | همان فرمِ خالی | `RegisterGate` سه‌حالته: pending / form / redirect |
| ۳ | **توکنِ دسترسی منقضی می‌شد و هیچ‌جا تمدید نمی‌شد** | نشستِ «ظاهراً موجود» هر درخواستش ۴۰۱ ⇒ رابط فکر می‌کرد کاربر تازه است | `POST /auth/session/state/` با `refresh` توکنِ تازه می‌دهد (`state: "revived"`) |
| ۴ | تایپ‌های نیمه‌کارهٔ کاربر بعد از ترکِ صفحه می‌رفت | «اطلاعاتم ذخیره نشد» | `useRegisterDraft` — پیش‌نویسِ امن (بدونِ کد ملی و تاریخ تولد) |

## معماری در یک نگاه

```
             ┌────────────────────────────────────────────┐
             │  POST /api/v1/auth/session/state/          │
             │  (سرور = تنها منبعِ حقیقت)                 │
             │  access زنده؟  → session                   │
             │  access مرده + refresh زنده؟ → revived     │
             │  شماره + کد ملی؟ → claim (دستگاهِ تازه)     │
             │  هیچ؟ → no_session                         │
             └───────────────┬────────────────────────────┘
                             │  { state, next{path,label,reason}, … }
                             ▼
        ┌────────────────────────────────────────────────┐
        │  src/shared/api/identity.ts  (کشِ سه‌لایه)     │
        │  ۱) اِسنپ‌شاتِ localStorage  → فریمِ اول، بی‌پرش │
        │  ۲) کشِ حافظه‌ای 20s         → کلیک‌های پیاپی     │
        │  ۳) single-flight           → یک درخواست        │
        └───────────────┬────────────────────────────────┘
                        │  useIdentity()
        ┌───────────────┴───────────────┬────────────────┐
        ▼               ▼               ▼                ▼
    EntryCta    RegisterGate     ExamRunner        AccountView
   (هدر/موبایل)  (/register)     (/exam)           (/login)
```

## سه قاعده‌ای که نباید شکسته شوند

**۱) هیچ‌وقت کاربرِ دارای پرونده «تازه‌وارد» نشان داده نمی‌شود.**
اگر شبکه خطا داد و اِسنپ‌شات یا نشستی موجود است، `state: "offline"` با
`stale: true` برمی‌گردد و مقصد همان `/exam` می‌ماند. تنها حالتی که فرمِ
ثبت‌نام نمایش داده می‌شود، پاسخِ صریحِ `no_session` از سرور است.

**۲) سرور تصمیم می‌گیرد، رابط نمایش می‌دهد.**
`next.path` و `next.label` از `/auth/session/state/` می‌آیند. هیچ کامپوننتی
حق ندارد خودش شرطِ `if (اعتبار آزمون)` بسازد؛ همین پراکندگی بود که چهار
حقیقتِ متفاوت ساخت.

**۳) حافظه‌های محلی «امتیاز» هستند، نه «ضرورت».**
هر نوشتن در `localStorage` در `try/catch` است. حالتِ ناشناس، حافظهٔ پر،
یا مرورگرِ سخت‌گیر ⇒ فقط کش از دست می‌رود، هرگز فرم نمی‌شکند.

## حریمِ دستگاهِ اشتراکی

پیش‌نویسِ فرم **فقط** نام، نام خانوادگی، شماره و مسجد را نگه می‌دارد
(allowlist صریح، نه `JSON.stringify`). کد ملی و تاریخ تولد عمداً نوشته
نمی‌شوند؛ روی گوشیِ امانی یا کافی‌نت نباید بمانند. با `clearDraft()` و
`invalidateIdentity()` هنگام خروج، هیچ ردی نمی‌ماند.

## امنیت

* `refresh` دقیقاً مثلِ `/auth/token/refresh/` سنجیده می‌شود: امضا، نوع،
  **و** زنده بودنِ `AuthSession`. نشستِ باطل‌شده (`logout-all` یا ابطالِ
  ادمین) با refresh هم زنده نمی‌شود — تست: `test_revoked_server_session_is_not_revived`.
* «Claim» (دستگاهِ تازه) نیازمند **شماره + کد ملی** با هم است؛ شمارهٔ تنها
  نشست نمی‌دهد. ریسکش دقیقاً همان سطحِ فرمِ ثبت‌نام است، نه بیشتر.
* حساب‌های ادمین از مسیرِ claim شرکت‌کننده نشست نمی‌گیرند (مسیرشان رمز است).
* با `BALE_OTP_MANDATORY=True` مسیرِ claim خودکار به `verification_required`
  می‌افتد. ⚠️ این همان هشدارِ ثبت‌شده است: در آزمونِ رسمیِ امتیازدار باید
  روشن باشد.
