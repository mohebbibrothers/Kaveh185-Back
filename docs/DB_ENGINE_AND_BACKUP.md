# موتورِ دیتابیس و روشِ درستِ پشتیبان‌گیری

## چرا این سند نوشته شد؟

در راهنمای دورِ ۵۱ نوشته بودم «قبل از هر چیز: `cp db.sqlite3 ~/db-backup-…`».
روی هاست اجرا شد و جواب داد:

```
cp: cannot stat 'db.sqlite3': No such file or directory
```

یعنی **دیتابیسِ تولید SQLite نیست**. اگر همان توصیه را ادامه می‌دادیم، نتیجه
دو چیز بود:

* **توهمِ امنیت**: خیال می‌کردید نسخهٔ بازگشتی دارید و نداشتید — بدترین نوع
  خطا، چون فقط روزِ حادثه معلوم می‌شود؛
* و یک ریسکِ **بی‌ربط** که تمامِ دورِ ۵۱ دربارهٔ آن هشدار می‌داد: قفلِ سراسریِ
  SQLite (`database is locked`) روی MySQL/MariaDB **وجود ندارد**.

پس این سند دو کار می‌کند: می‌گوید چطور موتور را قطعی تشخیص دهید، و پشتیبانِ
درست را نشان می‌دهد.

## ۱) تشخیص — یک دستور، بدونِ حدس

```bash
cd ~/Kaveh185-Back
bash deploy/check.sh
```

در بخشِ «موتورِ دیتابیس» یکی از این دو را می‌بینید:

```
✔ MySQL/MariaDB — قفلِ سراسریِ SQLite این‌جا موضوعیت ندارد.
✔ SQLite با بک‌اندِ ما (WAL فعال)
```

یا اگر `.env` را داشته باشید:

```bash
grep -E '^\s*DB_(ENGINE|NAME|HOST)' ~/Kaveh185-Back/.env
```

## ۲) اگر MySQL/MariaDB است (وضعیتِ فعلیِ هاست)

### پشتیبان — یک دستور

```bash
bash ~/Kaveh185-Back/deploy/backup-db.sh
```

این اسکریپت سه کاری می‌کند که نسخهٔ دستی نمی‌کرد:

* **ابزارِ درست را انتخاب می‌کند.** روی MariaDB 11، `mysqldump` «منسوخ» اعلام
  شده و پیام می‌دهد «از `mariadb-dump` استفاده کنید». اسکریپت اول
  `mariadb-dump` را می‌بیند و فقط اگر نبود سراغ `mysqldump` می‌رود. (پیامِ
  منسوخیت خطا نیست، ولی وسطِ آزمون یک هشدارِ قرمزِ بی‌مورد می‌سازد.)
* **پشتیبان را راستی‌آزمایی می‌کند**: حجم، سلامتِ `gzip -t`، و وجودِ
  `CREATE TABLE`. پشتیبانی که باز نمی‌شود، پشتیبان نیست.
* **هرس می‌کند**: ۱۴ نسخهٔ آخر می‌ماند (با `K185_BACKUP_KEEP` عوض می‌شود).

نسخهٔ معادلِ دستی (اگر خواستید خودتان بزنید):

```bash
cd ~/Kaveh185-Back
set -a; . ./.env; set +a
mkdir -p ~/k185-backups && chmod 700 ~/k185-backups
mariadb-dump --single-transaction --quick --default-character-set=utf8mb4 \
  -h "${DB_HOST:-localhost}" -u "$DB_USER" -p"$DB_PASSWORD" "$DB_NAME" \
  | gzip -9 > ~/k185-backups/db-$(date +%Y%m%d-%H%M).sql.gz
```

* `--single-transaction` یعنی **بدونِ قفل‌کردنِ جدول‌ها** — پس این کار را
  می‌شود وسطِ آزمون هم کرد (کمی کند می‌شود، ولی سایت نمی‌خوابد).
* ⚠️ فایلِ پشتیبان شاملِ کد ملی و شمارهٔ همهٔ شرکت‌کننده‌هاست. جای آن `600`
  باشد و در `public_html` نگذارید:
  `chmod 600 ~/k185-backups/*.sql.gz`
* **بازگردانی را یک بار تمرین کنید** (روی یک دیتابیسِ خالی)، نه روزِ حادثه.

### تنظیماتی که روی MySQL مهم‌اند

| تنظیم | پیشنهاد | چرا |
|---|---|---|
| `innodb_buffer_pool_size` | ۶۴ مگابایت یا بیشتر | کمتر از این، خواندن‌ها به دیسک می‌خورند |
| `max_connections` | حداقل ۳۰ | Passenger چند پروسه دارد و هر کدام یک اتصال می‌گیرد |
| `DB_CONN_MAX_AGE` | ۶۰ | جلوگیری از هزینهٔ handshake در هر درخواست |
| `wait_timeout` | ۳۰۰ | کمتر از این، اتصال‌های بی‌کار وسطِ آزمون می‌میرند |

`deploy/check.sh` مقدارِ `innodb_buffer_pool_size` را چاپ می‌کند (و اگر کمتر از
۶۴ مگابایت بود، `▲` می‌دهد).

## ۳) اگر SQLite است

بک‌اندِ `apps.core.db_sqlite` فعال است (WAL + `busy_timeout`). پشتیبان:

```bash
cd ~/Kaveh185-Back
# ⚠️ در حالتِ WAL، فقط cp کافی نیست: فایلِ -wal هم باید بیاید.
sqlite3 db.sqlite3 ".backup '$HOME/db-backup-$(date +%H%M).sqlite3'"
```

یا اگر `sqlite3` نیست: `cp db.sqlite3 db.sqlite3-wal db.sqlite3-shm` **در
لحظه‌ای که نوشتن نداشته باشیم** (بازهٔ بین دو آزمون).

## ۴) نقشهٔ ریسک‌ها بر اساسِ موتور

| ریسک | SQLite | MySQL/MariaDB |
|---|---|---|
| قفلِ سراسری حینِ نوشتن | **بالا** (رفع شد با WAL) | ندارد |
| اتصال‌های تمام‌شده در پیک | کم | **متوسط** (`max_connections`) |
| کندیِ گزارش‌های تحلیلی | بالا | **متوسط تا بالا** (بافرپول) |
| پشتیبانِ ساده با `cp` | کار می‌کند | **کار نمی‌کند** |

یعنی از آن سه ریسکی که در دورِ ۵۱ بستم، **یکی (قفلِ SQLite) روی هاستِ فعلی
موضوعیت نداشت**؛ دو تای دیگر (گزارش‌های سنگین و کشِ سرریز) مستقل از موتور
بودند و همان‌جا می‌مانند. ابزارِ جدید (`deploy/check.sh`) همین را صریح نشان
می‌دهد تا کسی دوباره در مسیرِ اشتباه نرود.
